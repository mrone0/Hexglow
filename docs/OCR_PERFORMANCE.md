# OCR 离线性能验证

## 当前策略（2026-10-14）

屏幕 OCR 只读海克斯区域：边框定位检查整段边缘带，保留原裁剪锚点；已知自有侧栏遮挡区域及其边界不参与边缘证据。边框定位不可靠时，尝试三个对齐、宽度及间距一致的卡片内部区域作为弱布局回退，再裁共同标题条带，卡片间空隙置黑。区域提示不是候选身份，仍须实际文字、原空间消歧及匹配校验。Tiny 未可靠识别时，Small 只读同一帧中的标题或三张卡片内部，整组替换、不混合结果。两种定位均不成立、四张卡片或竞争的两排布局继续返回 `choice-region-unavailable`，不回扫游戏场景。未知渐变或严重遮挡布局仍可能无法定位，不能宣称覆盖所有样式。手动截屏也遵循此范围，开发图片检查保留原图管线。

用户提供的棱彩及银色原图，以及保留文字的小范围平移变体，都经过与运行时相同的截屏区域计算和处理入口重放，三个候选 ID 与期望一致。另验证无边框可读样本、错位标题回退、坐标还原及背景排除。原先的三个失败场景保持原期望并已通过；这些是离线正确性检查，不是实战耗时／帧率验证。

定位不确定只撤销新的分析证据，不累计为面板消失、不关闭／重开侧栏、不重发旧排名。已有窗口显示“此前候选 · 复核中”，暂不显示旧评分和综合推荐；重新实际确认本组后恢复已有有效结果。已发出的模型请求仍保持在途状态，实际模型失败不被改写成等待。失去前台、真正空识别及换轮继续走原处理，不由像素提示认定已选完。

侧栏展示另有独立保护：同组“定位不确定”状态持续约 3 秒且鼠标未停在侧栏内时，复用原生窗口 watcher 折叠为把手，不隐藏／清空窗口内容、不停止 OCR、不调用模型。真实同组识别恢复、用户交互或局／轮／候选组变化会重置该计时；重复状态和模型在途不延后计时。前端只在真实同组 OCR 恢复后还原此前分析状态，不强行重新展开原组。3 秒是界面收起策略，不是选择完成或游戏进度判据；原 20 秒无交互收起仍保留。

本次增加已处理候选的轻量标题监测：只有本组已发起过分析／已有保存结果／自动次数用尽，且没有分析在途时，才允许使用。后端必须已连续两次完整推理识别同局同阶段同组三项，并能从真实识别坐标定位三个精确标题。此后仍截取新画面，只逐字节比较标题附近像素；变化立即进入完整 OCR，不变最多延后 3 秒再走完整识别路径（该路径仍可能命中原有五秒整帧精确缓存）。尺寸、局／轮／候选 ID 不符、标题不完整或比较异常时不延期。动画、遮挡或未知布局可能使监测失效，回到完整 OCR。

轻量响应标记 `probeOnly/unchangedPanel`，文字和候选为空，不计 OCR 命中、不充当第二次稳定识别、不允许新模型请求。它也不是“面板消失”：保留已显示结果，但清除新的分析授权证据。刷新组仍须两次新鲜完整识别及同轮接口确认；没有在途分析时才降负载，不牺牲在途结果的新鲜度。只在内存保存最多 512KB 标题区域像素，不写入档案或屏幕文件；日志仅记录 `panel-unchanged` 等固定原因。

OCR 明确配置 CPU provider，仍采用低优先级单线程、无自旋。核对锁定依赖的 Cargo feature 后确认，它没有编译 `api-22` 下的自动设备选择路径；此前只看到 DirectML 加载而怀疑 GPU 的判断不足，不能据此声称旧包 OCR 使用了 GPU。本次未更换或补丁依赖。侧栏已显示且展开时，评分／内容更新不再重复改尺寸、定位或重启 watcher；重复关闭已经隐藏的空侧栏也不再发清空事件。实际掉帧改善尚未测量。

选人／加载期间提前预热并持续采集接口；首轮只在当前局实际 `GameStart` 事件出现后唤醒，不按加载时长或游戏时间推测、不额外等 3 级或阵容。完整 Live 数据没有该事件时，在有效 LCU 同局身份下补读 `/liveclientdata/eventdata`（最多 250ms）。后续使用实际 7／11／15 等级；缺等级不从后续阶段退回首轮。中途接入且缺等级时不把保留在事件列表中的旧 `GameStart` 当新开局，恢复档案也不算本次运行观察过加载。

自动扫描在截屏前检查实际推理就绪标志，未就绪立即返回预热状态，不排队等待模型锁，前端约 250ms 后检查。初始化失败明确报告；忙碌不是预热失败，不消耗失败预算。仍保留单任务、前台校验、两次新鲜同组识别、同局同轮确认和每阶段最多 4 次自动分析。

当前采样为居中 90% 宽、52% 高，仅用于像素定位，并在内存遮挡自有侧栏；截屏同时传递实际遮挡矩形，不根据黑色像素猜窗口位置。神经网络只处理海克斯区域。Tiny 完全无线索时 Small 有独立安全回退预算，回退也不超出卡片。日志 `roi/roiMode/roiOrigin` 记录首遍输入尺寸、模式及边框／内部回退来源，`regionReason` 记录边框定位的固定原因代码；Small 必要时可扩大到卡片内部。这些计时只控制重试负载，不猜游戏是否开始。下面按日期保留历史实现及测量。当前策略没有实战端到端延迟或 FPS 测量，不作速度保证。

## 初始实现与边界（历史）

保留原来的 PP-OCRv6 Small 检测模型、默认检测尺寸与阈值，以及完整截图区域；只把第一遍文字识别换为 PP-OCRv6 Tiny。全部原始文字先通过现有 `match_augments` 的空间布局与唯一候选组检查，再要求高置信度（至少 0.95）、精确名称子集独立匹配出同样的三个 ID。未满足时，对同一帧完整运行 Small 识别，整组替换结果，不跨遍拼接候选。

Tiny 推理失败会回退；Tiny 文件缺失、尺寸错误或模型加载失败也可以仅使用 Small。构建和安装验证仍要求清单中的五份资源完整、哈希正确。Small 的必需资源损坏仍报告安装错误。运行时不下载模型，不新增推理服务调用。更换识别模型不绕过两次真实稳定观测、授权、次数限制和冷却规则；当前每轮自动分析最多 4 次，覆盖初始候选和三张卡各一次刷新。

预热在应用启动后台完成，使用编译进程序的合成卡片图真正执行检测和识别，而非仅创建模型会话；不截取桌面、不写入候选缓存、档案或收费次数。扫描移到 blocking worker，避免同步推理占用异步执行线程。

快路和回退使用两个 OAROCR 管线，各自持有检测器与线程池，因此有额外驻留内存开销。新增模型与字典约 4.49 MB，全部模型资源合计 35,604,632 字节。不得用单个 Tiny 管线的耗时冒充最终双管线性能。

## 游戏优先资源限制（2026-10-13）

最新配置把每个 ONNX 会话的 intra-op 和 inter-op 线程数固定为 1，关闭图节点并行执行，并明确关闭 intra-op / inter-op 空闲自旋。Tiny 和 Small 管线继续串行执行，预热也使用同一限额。此处的单线程用于减少游戏开局阶段的 CPU 争用，不保证 OCR 单帧更快。

oar-ocr 的缩放、归一化及 CTC 解码还会使用 Rayon，因此整个 `predict` 放入一个复用的私有单线程池。Windows 上该私有线程保持低于普通线程的优先级；预热和扫描的 blocking worker 临时下调优先级，任务结束或异常时恢复。游戏进程和应用主线程不改优先级，也不改进程全局 Rayon 环境。额度不是整个 Hexglow 的 CPU 百分比承诺。

自动截屏仅检查当前前台窗口的游戏身份，不再为了查找后台游戏而枚举所有窗口。可见性、最小化和截屏前后焦点校验保留；截图范围和识别可靠性门槛不改。加载期间的跳过原因采用固定代码，按状态变化限速记录，不打印标题、玩家或画面内容，也不计入真实 OCR 扫描次数。

合成预热同时使用原 fixture 和典型 16:9 客户区的中心截图尺寸（1587×748），提前准备较接近真实面板的推理输入。预热仍不抓取屏幕、不更新候选缓存。刷新候选时，英雄或装备变化不会重新展开同一组侧栏。

### 2026-10-13 日志观察

用户反馈掉帧发生在侧栏显示前。00:49:40 的 OCR 启动预热耗时 722ms，00:49:59 已完成选人期的侧栏预载。00:50:44 首次实际截屏耗时 23ms，识别约 390ms；之后稳定识别约 130–170ms。首次完整候选到评分显示约 2.5 秒，模型请求往返约 0.54 秒。日志不含游戏帧率，因此不能据此断定 0 帧的唯一原因。

00:56 一局的首轮同时与本地打包验证重叠（安装包在 00:57:31 生成），这会给性能比较增加后台构建负载。新的打包脚本默认 2 个编译任务，并下调打包进程优先级；复测应在没有构建任务的情况下进行。上述日志来自本次单线程改动之前的安装包，不是新配置性能结果。

缓存仍只接受完整截图像素完全相同且五秒内的结果，任何像素变化立即失效。不使用模糊截图相似度或只比较标题区域来复用旧候选；Tiny 的可靠性门槛、Small 回退以及候选匹配规则不变。

### 2026-10-13 晚间复测与调度修正

21:21:25 的首轮真实扫描耗时 2213ms：截图 18ms、Tiny 689ms、Small 回退 1499ms；这次不是模型响应慢，模型请求被旧每日总上限拦截。21:21:33 才执行下一次真实扫描，旧调度按推理耗时的三倍追加等待，进一步放大延迟。首轮前曾记录 `game-not-foreground`，但旧诊断只记录状态变化，不能据此证明整个等待期间游戏始终不在前台。

每日总限额已经移除，每个海克斯选择阶段自动分析仍最多 4 次、失败也计数、新阶段和新局独立计数。21:40 的候选包限制了完整候选后的额外等待，但漏读仍可能进入三倍耗时退避，因此不是最终调度方案。

21:56 的复测确认另一处延迟：先识别出三张候选，接着一帧漏读耗时 3277ms（Small 回退 2418ms），随后约 10 秒才重扫。第一次成功识别到保存评分约 17 秒，模型请求往返约 1.4 秒。这说明“首次成功后立即漏读”不能直接当作进入战斗阶段。

最新调度按“本局 + 海克斯等级阶段”保存独立窗口：

- 开局或进入 7／11／15 等级阶段时立即唤醒扫描，不继承旧阶段退避；进行中的单个 OCR 仍须完成，不能并发叠加。
- 第一次实际非跳过扫描起的 60 秒为发现窗口，未找到面板时额外退避最多 3 秒。游戏不在前台等跳过不启动该窗口；当前版本在实际开局信号首次满足条件时清除首轮退避一次，不按游戏时间推测。
- 最近 12 秒内成功识别过面板，随后短时漏读时额外等待 700ms；每次真实面板识别成功延续这个窗口。该时长是调度策略，不是游戏的选择倒计时。
- 持续缺失、窗口结束后转为低频探测，额外等待至少 10 秒；昂贵扫描仍保留三倍耗时退避，上限 60 秒。低频阶段没有被当成“已选择”的业务证据，之后实际识别到面板可恢复快速复核，新等级阶段可立即重新唤醒。

推理自身耗时另计，不承诺 700ms 内完成分析。漏读会清除模型稳定观测，不使用旧候选补造第二帧；两次真实稳定观测、轮次新鲜度和授权校验均保留。调度修改没有更换识别模型、降低可靠性阈值或缩小截图范围。22:17 已直接构建替换进行调度复测。

### 像素级面板探测（晚间追加修正）

在相同的真实截图上最多取样 128×80 点，用暗色平坦区域、卡片分隔和纹理判断 `likely / uncertain / unlikely`，不运行神经网络、识别文字或输出候选。它是采样时机提示，不是面板可见性的人工真值，也不是识别准确率。

- 疑似卡片面板直接进入完整 OCR；真实识别到面板后的 12 秒内也不因探测器偶尔漏判而挡住完整复核。
- 不确定样式首次运行完整 OCR，之后至少间隔 2 秒再做完整回退；高纹理或空白画面的新阶段允许先轻量探测，3 秒后做首次安全回退，后续完整回退至少间隔 20 秒。完整回退的间隔从上次推理完成时计算，推理本身仍可能很慢；仅有暗背景和明亮 HUD 不再直接判为疑似卡片。
- 没有进入完整 OCR 时，前端按完成后至少 500ms 的预算继续轻量探测；完整 OCR 漏读后也回到这个轻量节奏，由后端独立限制下一次昂贵推理，避免继承十几秒等待或持续满负载重试。仍只有一个扫描任务。主窗口隐藏时沿用后台唤醒，断线、失去前台或快照过期仍暂停。
- 探测结果带 `probeOnly=true`，候选与文字为空，不进入 OCR 命中统计或模型稳定观测。不把两次探测当成两次识别；就算异常响应附带旧候选，前端也拒绝由它触发分析。
- 显式手动完整扫描和图片 fixture 不经过探测门控，未知/无效阶段参数回退为完整扫描。候选匹配、Tiny 置信度和 Small 整组回退规则不变。

新增 `panel-probe-stats.json` 单独记录探测、完整推理、三张候选输出和帧缓存计数；旧 `ocr-stats.json` 的累计历史保留，不重置、不补造画面真值。界面去掉了全历史比例的“准确率”暗示，只展示分别计数。无推理的探测日志按状态变化或至少 10 秒一次限频，日志只输出阶段、判定、耗时与计数，不保存屏幕或文字。

验证包含合成三卡、缩放、部分裁切、空白/纹理负例，以及用户提供的棱彩面板参考图及中心裁切。仅这些样本通过不能证明所有主题或真实动画不会误判；未知样式回退可能增加延迟，需以新版实战探测日志核对。不将像素取样上限换算成已测得的 FPS 或端到端速度改善。

本次目的是减少与游戏的 CPU 争用、空闲忙等，不保证单帧 OCR 自身更快。此前强制少线程的探索曾出现单帧耗时增加，因此前端也必须留出推理后的空闲时间，不能用更密集的重试抵消线程限制。为避免影响用户正在进行的游戏，本次只做配置/缓存回归和短合成 fixture 检查，未运行长时性能基准，也未测量实际游戏帧率。**下列数据属于改限额之前的历史基准，不能用作当前配置性能声明。**

### 无候选帧不再逐帧追加 Small，以及采样范围修正

23:22 的第 15 等级阶段，在首次三候选输出前仍有一次 4541ms 的空扫描，其中 Tiny 1025ms、Small 回退 3491ms。成功帧自身为 683ms，模型往返 653ms；阶段首次扫描到首次成功的 17.71 秒包含尚未知是否可见的面板时间，不能当作实际可见后的识别延迟。

有效自动扫描阶段改用独立的空结果回退预算：Tiny 未找到任何可信标题线索时，不再每帧追加 Small，而是返回空候选继续取新画面。首次阶段和上次 Small 完成至少 6 秒后的安全检查仍执行完整回退；任一精确/保守模糊标题线索、低于快路门槛的候选或 Tiny 错误均立即回退。手动扫描、图片、无效阶段参数保持原完整管线。三标题 0.95 置信度、空间匹配、两次稳定识别和模型授权门槛不变。

被延期的 Tiny 结果不输出文字或候选，也不复用帧缓存，防止相同画面压住定期安全检查。它仍属于真实 Tiny 推理，计入 OCR 扫描数，日志标记 `reason=empty-fallback-deferred`、`fallback=0ms`，不与纯像素探测混淆。此预算仅减少空帧阻塞，不降低已有成功结果的校验门槛，也不保证所有帧都更快：Tiny 完全漏读标题时，恢复可能依赖定期 Small，增加最多一个预算间隔（另计扫描调度及推理时间）。实战帧率和真实候选出现后的延迟仍需复测。

对用户提供的 2149×1055 棱彩面板做实际离线推理时，原居中 62% 横向范围裁掉了左侧标题，完整 Small 路径也只找到两个标题线索、未形成候选面板。这是该样本的确定缺口，不能直接推断近期每一帧漏读的原因。当前保留居中 52% 的纵向范围，横向扩到 90%，同时按已注册的 Hexglow 侧栏 HWND、物理窗口矩形遮掉自有界面的重叠区域，避免重复名称产生歧义。只在内存中遮挡，不隐藏/移动窗口、不保存截图、不枚举其他应用；遮住的游戏内容无法凭空恢复。

同一原始参考图：旧范围候选为 0；新范围加侧栏遮挡时，在完整回退策略与空帧延期策略下均按左到右识别出正确三个 ID，快路为 Tiny。保留这个可选离线回归及旧失败预期，不把它算作全场景准确率或游戏帧率测试。预热的大尺寸输入随新采样比例调整为 2304×748，仍只用合成样本。

## 历史本机测量（2026-10-12，资源限额之前）

机器：Intel Core i5-13600KF，Windows，CPU ONNX Runtime，oar-ocr 0.9.2，Rust release 模式。没有使用游戏截图、游戏 API 或付费模型。图片解码在计时外，OCR、文本整理、候选匹配在计时内；不含截屏、前端复核等待、知识检索、推荐服务往返和发布。

| 配置 | 中位耗时 | P95 | 符合预期图数 |
| --- | ---: | ---: | ---: |
| 旧 Small 检测 + Small 识别，batch 8 | 133.1 ms | 172.0 ms | 220 / 221 |
| 新 Small 检测 + Tiny 识别，Small 回退 | 85.5 ms | 251.8 ms | 220 / 221 |

中位耗时下降约 36%。171 图直接采用快路，50 图执行回退；快路错误放行 0，负例错误候选面板 0。**回退路径会更慢，P95 本次变差，不能宣传所有识别都提速。** 两种方案都在 `catalog-041-size-20` 漏读一项（期望 ID 1358、1361、1373，只得到后两项）；此缺口明确保留，未修改期望标签，也没有用猜测补齐。回归门槛为不新增旧方案能正确识别的失败图、快路不放行错误 ID、负例不放行。

## 复现

在仓库根目录运行（Python 需要 Pillow 与本机微软雅黑字体，脚本支持 `--font` 指定本地 CJK 字体）：

```powershell
pnpm prepare:ocr
python scripts/make-ocr-benchmark-corpus.py
cargo test --manifest-path src-tauri/Cargo.toml --offline --locked --release --lib ocr::tests::benchmark_production_corpus -- --ignored --nocapture --test-threads=1
```

性能测试单独运行，不同时启动其他基准。日常 `cargo test` 默认跳过此耗时基准；不会启用另一个需要真实前台游戏的忽略测试。生成物仅在 `src-tauri/target/ocr-benchmark-corpus`，不进入真实用户数据目录。

单模型探索可使用 `src-tauri/examples/ocr_benchmark.rs`；Small/Tiny 识别资源均从已校验的资源目录读取。可选 Tiny 检测器仅为实验项，不打包，需自行放到被 Git 忽略的 `src-tauri/target/ocr-benchmark-models` 并核对上游清单。

日志保留原有 `source/cached/lines/matched/bytes/elapsed`，新增 `acquisition/recognition/matching/fast/fallback/engine/reason`。`recognition` 包含模型锁等待、必要初始化和快路选择检查；`fast`、`fallback` 是各推理遍的耗时。缓存命中会把两遍推理时间清零，但仍保留原结果来源，不计为新 OCR 推理。日志不打印识别文本、玩家名或画面内容。

启动预热日志还记录 `cpuThreads/intraSpin/interSpin`，便于确认运行包采用新限额；线程策略配置存在并不等于已测得游戏帧率改善。
